Service-to-service authentication · Architecture overview02

The three services

Each has one job. Service A and service B are ordinary application services; the auth service is the only one that knows anything about credentials.

What travels between A and B

Only a bearer token: tra_at_9f2c…. It expires in ten minutes and is valid at service B and nowhere else.

What never travels

The application secret. It goes to exactly one endpoint, POST /oauth/token, and no further.

ServiceRoleWhat it holds
auth-service Issuer and verifier The registry, every secret hash, the token pepper, the administrator key
service-a Caller Its own client id and secret — nothing else
service-b Resource server Its own client id and secret — nothing else

All three are LoopBack 4 applications. A service becomes part of this scheme with one call at start-up and a decorator on each endpoint it wants protected; the verification, caching and refresh logic is shared.

Service-to-service authentication · Architecture overview03

One request, end to end

Everything below happens on a single call from service A to service B. Steps ① and ④ are cached, so a busy service performs them a few times a minute, not once per request.

The secret appears once

Step ① is the only place in the system that accepts one. Steps ② to ⑤ carry a token that is useless anywhere but service B.

Two caches, two dials

Service A caches the token for its lifetime; service B caches the verification for 30 seconds. The second dial is revocation latency.

Cost per request

In steady state, ② and ⑤ only. The auth service sees roughly two calls a minute per distinct token, not one per request.

Managing the application registry · Architecture overview04

What the auth service stores

Four records. The application is the one you curate — it is where you describe who a caller is. The rest are produced and retired by the system as it runs.

You maintain one of these

The application. Everything else is written by the system as it runs: secrets when you ask for one, tokens on every exchange, audit rows on every event.

Nothing here is reversible

secretHash and tokenHash are one-way. There is no endpoint, and no query, that returns a usable credential — including for an administrator.

Managing the application registry · Architecture overview05

Adding data to an application

Anything recorded against an application travels with every token it uses, and arrives at the resource server as fact. The caller never handles it, so it cannot forge it.

Worked example — adding a new attribute

Service B needs to route some callers to a different region. There is no schema change, no migration and no release of the auth service.

1 · Record it

PATCH the application with

"metadata": {"region": "eu-west"}

2 · It propagates

Within 30 seconds every resource server sees it on the next verification.

3 · Use it

Service B reads caller.app.metadata.region and routes accordingly.

The same path carries tenancy, rate limit tiers, cost centres, data residency rules — anything a resource server should know about a caller but must not take the caller's word for.

Managing the application registry · Architecture overview06

The management surface

One API, behind an administrator key. It is a different trust domain from service traffic — it creates the credentials everything else depends on, so it does not ride on the tokens it issues.

EndpointWhat it is for
POST /admin/applicationsRegister a caller. ?issueSecret=true returns its first secret in the same response.
PATCH /admin/applications/{id}Add or change the data a resource server sees — team, owner, contact, environment, tags, metadata, permissions.
GET /admin/applicationsList, filtered by environment, team, tag or status.
GET /admin/applications/{id}One application with its secrets and live token count.
POST …/{id}/suspend
POST …/{id}/activate		Reversible kill switch. Stops issuance and revokes outstanding tokens; keeps the history.
POST …/secretsIssue a credential. Plaintext returned once, stored only as a hash.
GET …/secretsStatus, expiry, last use — metadata only, never a hash.
POST …/secrets/{id}/rotateIssue a replacement and put the old one on a countdown.
PATCH …/secrets/{id}/expiryShorten a suspect credential, or extend one about to lapse.
DELETE …/secrets/{id}Revoke now, along with every token the secret minted.
GET /admin/auditEvery credential event, filtered by application, type or outcome.

An importable Postman collection covers all of this — 42 requests, including the failure cases, each asserting its own expected outcome.

Credential lifecycle · Architecture overview07

Secrets: many at once, on purpose

An application may hold several secrets simultaneously. That is what makes rotation uneventful: the replacement is live before the old one dies, so there is never a moment when nothing works.

Expiry is not optional

Every secret is issued with an expiry — 180 days by default. It is enforced at the moment of use, so it is exact. A background sweeper marks lapsed secrets and retires dead tokens.

Stored as a hash

Only a scrypt hash is kept. The plaintext appears once, at creation. A database leak yields nothing usable, and losing the value means issuing another rather than recovering it.

Rotation, in practice

#StepHow you know it worked
1Request a rotation with a window longer than a deploy takesThe response carries the new secret and the date the old one stops working
2Put the new value in your secret store and roll the deploymentServices pick it up on restart; no coordination between them is needed
3Watch the two secretslastUsedAt on the old one stops advancing while useCount on the new one climbs
4Revoke the old secret, or let the window close itIt disappears from the usable list

When something goes wrong

Four levers, in increasing blast radius. Reach for the narrowest one that covers the problem.

Credentials are held separately

Each service reads only its own configuration. One compromised service does not become every service.

Summary · Architecture overview09

In short

The mechanism

  • A secret is exchanged for a short-lived token at one endpoint.
  • The token is opaque and bound to a single recipient.
  • The recipient verifies it with the issuer, and caches the answer.
  • No certificates, no signing keys, no key distribution.

The management model

  • Applications are registered and described centrally.
  • That description reaches every resource server as fact.
  • Secrets are issued, rotated and revoked without a redeploy.
  • Every credential event is recorded.

Properties worth restating

PropertyHow it is achieved
A compromised service B cannot impersonate service AB only ever receives a token minted for B.
A leaked credential is contained in one callRevoking a secret revokes every token it minted.
A database leak yields nothing usableSecrets are scrypt hashes; tokens are HMACs under a pepper held outside the database.
Probing reveals nothingWrong secret, unknown application and malformed credential all return one indistinguishable response, in the same time.
An outage does not become an openingIf the auth service cannot be reached, resource servers refuse the request.
Callers cannot lie about themselvesTheir profile comes from the registry at verification time, never from the request.

Before production

  • TLS on every hop — the secret crosses the network once.
  • Move storage from the in-memory connector to PostgreSQL.
  • Replace the shared administrator key with per-operator identity behind SSO.
  • Run more than one replica: every call depends on this service.
  • Back up the token pepper; losing it forces a fleet-wide re-authentication.
  • Alert on denied and throttled token requests, and on secrets nearing expiry.
